# doc-review — 変更単位のドキュメントレビュー

**発動条件**: `CLAUDE.md`・`README.md`・`CHANGELOG.md`・スキル(`.claude/skills/`)など、リポジトリに入る文書に意味のある変更を加えた作業の締め。字句だけの修正(typo・表記ゆれ、同じ文書・節の移動先へのリンクの張り替え)なら不要。ユーザーの指示を待たず自発的に実行する。

対象は `.md`。`docs/` はローカル専用(`.gitignore` 対象)なので、レビューの対象にしない。

## 手順

### 1. 変更範囲の特定

`git status` / `git diff`(未コミットならワーキングツリー、コミット済みなら直近コミット)で今回変更された文書を列挙する。git管理外なら、このセッションで編集した文書を自分で挙げる。

### 2. 関連文書の読み込み

変更ファイルごとに「参照している文書・コード」「参照されている文書」を辿る。最低限、次を見る。

- `CLAUDE.md` を変えたなら、そこに書いたパス・コマンド・型・不変条件の実物(`package.json` の scripts、`frontend/shared/types.ts`、`src-tauri/src/types.rs` など)
- `CHANGELOG.md` を変えたなら、対応する PR・コミットの実際の変更
- スキルを変えたなら、そのスキルが名指す他のスキル・フック・スクリプトの実在

リポジトリ全体は読まない。

### 3. 5つの検査

| # | 検査 | 見るもの |
| --- | --- | --- |
| 1 | **コードとの整合** | 文書の記述が実装と食い違っていないか。**単体で正しくても組み合わせで穴が開かないか**(新しい規則と既存の規則の相互作用など)。移行途中の記述(「未実装」「残存」)が現状とずれていないか |
| 2 | **CHANGELOG の規則** | ユーザー向けの言葉で書かれているか。内部的な変更(docs / chore / refactor など)を載せていないか。`[Unreleased]` 節に追記されているか。カテゴリが正しいか |
| 3 | **参照整合** | リンク切れ、存在しないパス・コマンド・スキル名、節番号のずれ |
| 4 | **文言品質** | 結論先出し / 一文一義 / 専門用語の初出説明 / 「等」「適切に」の逃げ。`writing` スキルがあればそれに従う |
| 5 | **コード例** | 文書内のコード例・型定義(`Session` など)が最新の実物と一致しているか |

あわせて、**markdownlint を実行**する(プロジェクトの規則)。指摘は修正する。

### 4. 独立レビュアーの起用判断

- **`CLAUDE.md` の不変条件・アーキテクチャ記述を変えた**とき: 検査1のみサブエージェント(先入観のない敵対的レビュアー。[tdd スキルのモデル表](../tdd/SKILL.md)の `sonnet` で起動する)に委譲し、結果をメインの検査と突き合わせる。プロンプトには「関連するコードのパス」「矛盾・相互作用の穴を具体例で示せ」「深刻度を『覆す必要/規則追加で解決/軽微』で分類せよ」を含める。
- それ以外の変更: メイン自身がチェックリストで検査する(サブエージェントは使わない。コストに見合わない)。

### 5. 結果の処理

- **軽微(typo・リンク切れ・markdownlint 違反・スタイル違反)**: その場で修正し、修正内容を報告に含める。
- **設計に触れる指摘(矛盾・相互作用の穴・方針が未決の記述)**: 勝手に直さず「場所・問題・修正案」の形でユーザーに報告し、判断を仰ぐ。
- 指摘ゼロなら「doc-reviewクリア」と一言で報告する(長い報告を書かない)。

## やらないこと

- 全文書の総当たり検査(変更ファイルとその関連だけを見る)
- 設計判断そのもの(指摘と修正案の提示まで。決定はユーザー)
- コードのレビュー(`impl-review` の担当。使い分けの正は `.claude/README.md`)

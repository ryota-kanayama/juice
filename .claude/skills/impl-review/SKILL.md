# impl-review — 実装の変更単位レビュー

**発動条件**: コード(文書以外)の変更をコミットした作業の締め(push後、マージ依頼の前)。ユーザーの指示を待たず自発的に実行する。Stopフックが未実施を検知してブロックするため、忘れても機械的に発動する。

言語・ディレクトリ構成には依存しない。「コード」の範囲はフック(`impl-review-check.sh` の `EXCLUDES`)と揃える——**文書・`.claude/` 以外のすべて**。

## 手順

### 0. 前提の確定

- 比較元ブランチ: `git symbolic-ref --short refs/remotes/origin/HEAD` → 無ければ `main` / `master` / `develop` の実在するもの。
- テスト・整形・静的解析のコマンド: `CLAUDE.md` / `AGENTS.md` / ビルド設定から確定する(以降の検証で実際に走らせる)。

```text
base=$(git merge-base "origin/<既定ブランチ>" HEAD 2>/dev/null || git merge-base "<既定ブランチ>" HEAD)
```

### 1. 差分の特定

`git diff "$base"...HEAD` で今回のコード差分を取得し、関連する要件(Issue・PR の説明・`CLAUDE.md` の該当節。ローカルの `docs/plans/` があればそれも)と `test-writing` スキルを列挙する。

### 2. 敵対的レビュー(並列2観点)

サブエージェント2体を [tdd スキルのモデル表](../tdd/SKILL.md)の `sonnet` で並列起動する。共通の指示: 「LGTMを出すことが目的ではなく欠陥を見つけることが目的。指摘ゼロで返す場合は、検査した観点と『問題なし』の根拠を列挙すること(根拠なしの合格は不可)」。

- **観点A: 要件適合とテストの穴** — 差分と、その変更が満たすべき要件・不変条件(例: `CLAUDE.md` の「時刻の不変条件」)を突き合わせる。要件が定めるのにテストが無いエッジケース、正常系・異常系の対応漏れ、test-writing規約違反(曖昧検証・期待値の非明示・命名)を探す。**変異解析**(`test-writing` スキルの3類型)を指示に含める。
- **観点B: 実装品質** — 境界計算のずれ(off-by-one)、エンコーディング/型変換の落とし穴、異常系の経路(panic・未処理例外・エラーの握り潰し)、不変条件の破れ、並行性・リソース解放、言語のイディオム、静的解析が拾わない設計上の弱点を探す。

渡すもの: 差分全文 / 変更ファイルの全文パス / 関連する要件の所在 / `.claude/skills/test-writing/SKILL.md` / 検査観点。

- 縮退則: 差分が**テストのみ**(プロダクトコード無変更)の場合は**観点Aの1体**でよい(観点Bの検査対象がプロダクトコードのため)。
- 縮退則(スタイルのみ): 差分が**スタイルシートのみ**(`*.css`。CSS Modules を含む)の場合は、行数によらず**レビュアー1体**(観点B中心)でよい。かわりに、**変更した画面を変更の前後で撮影し、メインが目視で比べる**(撮影の手段はプロジェクトの `CLAUDE.md` に従う。ポップオーバーは blur で自動クローズするため撮影が難しい——撮れないときはユーザーに目視確認を依頼する)。観点Aの変異解析は、見た目の崩れを検知する網を持たないため効きが薄い。認証まわりの画面でも、差分がスタイルシートだけなら対象に含める
  - **操作やフォーカスに効く属性に触れたら縮退しない**(`pointer-events`・`display`・`visibility`・`cursor`・`outline`、`:focus` 系や `[data-disabled]` などの状態セレクタ)。画面を問わず2観点で回す。撮影は静止画しか比べないので、「見た目は同じまま押せるようになった」を検知できない。2観点で回すときも、触れた属性が操作性・フォーカスへ与える影響を観点に足して渡し、前後の撮影も行う
  - 1体に渡す観点は観点Bのうちスタイルに当たるものに置き換える: 規約の抜け穴(整形・静的解析の除外コメントの新規追加など)、カスケードと詳細度の崩れ、同じクラスを使う他の画面への波及、プロジェクトの規約が「レビューで見る」と委ねたスタイル上の項目(画面幅の分岐の置き場など)
  - 「前」は既定ブランチの状態で撮る(主作業ツリーか、既定ブランチから切った作業ツリー)。作業ブランチの変更を一時的に戻して撮らない
- 縮退則(小さな差分): 次の**すべて**を満たす場合は、**レビュアー1体**に2観点の指示をまとめて渡し(設定・ビルドのみの差分では観点B中心)、実行による機械検証(該当コマンドを実際に走らせる)で補えば足りる。レビューのコストを差分の規模に比例させる
  - 差分全体(`git diff --shortstat "$base"...HEAD` の追加+削除の合計。`$base` は手順0のもの)がおおむね20行以下
  - 設定・ビルドファイルのみ、または列挙できる機械的変更(整形のみ・コメントのみ・機械的リネーム)のみ
  - 認証・権限・秘密情報・CI の権限設定・DB 接続・外部送信に**触れない**(これらは行数によらず縮退しない)
  - 実行して確かめる機械検証のコマンドが1つ以上ある(無ければ縮退しない)

### 3. 指摘の分類と処理

| 深刻度 | 基準 | 処理 |
| --- | --- | --- |
| **重大** | 誤動作・仕様違反・不健全なAPI | 再現テストRed→Greenで修正する(`tdd` があればそれに従う)。テスト無しの直接修正は不可 |
| **改善** | このPR内で直す価値がある品質問題 | メインが直接修正し、全テスト+整形+静的解析を再実行 |
| **メモ** | 将来サイクルの課題 | テストリストまたはロードマップに追記(このPRでは直さない) |

### 4. 解消検証

重大・改善を修正したら、**同一レビュアー**(SendMessageで継続)に修正差分を渡して解消を確認する。依頼文には「**解消判定(解消/部分解消/未解消)と新規指摘のみを返す。未解消・部分解消には根拠を付し、全件解消なら確認箇所を `ファイル:行` の列挙で示す(説明文は不要)**」と明記する(検証ラウンドの出力肥大を防ぎつつ、根拠なしの合格を作らない)。新規指摘が出たら同様に処理。最大2ラウンドで収束しなければユーザーに判断を仰ぐ。

- 収束の軽量則: 検証ラウンドで出た新規指摘が**文書・コメントのみ**で、修正内容をレビュアーの提示文言と機械的に突き合わせられるなら、メインが修正・確認して収束宣言してよい。追加の検証ラウンドは重大・実装変更を伴う指摘が出たときだけ回す。

### 5. レビュー済みコミットの記録(必ず最後に)

修正コミットをすべて済ませた**後に**、レビューが及んだコミットを台帳へ追記する。

```text
base=$(git merge-base "origin/<既定ブランチ>" HEAD 2>/dev/null || git merge-base "<既定ブランチ>" HEAD)
mkdir -p .claude/state
git rev-list "$base"..HEAD >> .claude/state/impl-reviewed-commits
```

台帳(`.claude/state/impl-reviewed-commits`)は**追記のみ**で、実際にレビューした者だけが書く。ブロック通知の副作用でレビュー済みになることはないので、**通知を無視したまま完了することはできない**。

- **squashマージ後は追記しない**: squashはコミットハッシュを作り直すが、マージ後の既定ブランチはフックの対象外(既定ブランチは素通し)。
- 台帳は共有だが追記のみなので、同一作業ツリーで他セッションが動いていても壊れない。**作業ツリーごとに独立**するため、作業対象の作業ツリー側で追記する。

## 例外(レビューを回さないケース)

- **コード変更が無い作業**(文書のみ): フックが自動で素通しする。何もしなくてよい。
- **ユーザーが「レビュー不要」「レビュースキップ」と明示したとき**: レビューを省略し、対象コミットを**免除台帳**へ追記して、報告に「impl-review免除(ユーザー指示)」と明記する。レビュー済み台帳と別ファイルにするのは、後から「レビューしたのか免除したのか」を区別できるようにするため。

  ```text
  mkdir -p .claude/state
  git rev-list "$base"..HEAD >> .claude/state/impl-exempted-commits
  ```

- **既定ブランチへの直接コミット**(ユーザー指示時のみ発生): フック対象外。必要ならユーザーが手動で依頼する。
- 自明な機械的変更(整形のみ・コメント修正のみ)でも、省略はユーザーに確認してから。自己判断で免除しない。**縮退(1体で回す)と免除(回さない)は別物**で、ユーザー確認が要るのは免除だけ。

## 位置づけ

- テストが守るのは「テストに書いた挙動」。このスキルが検査するのは**テストリスト自体の穴**(要件の見落とし・エッジケース欠落)と実装の質で、両者は補完関係にある。
- より重い網として `/code-review ultra`(クラウド多エージェント・課金・**ユーザー起動のみ**)がある。フェーズ完了級の節目ではultraの実行をユーザーに提案する。

## やらないこと

- 文書のレビュー(スキル間の使い分けの正は `.claude/README.md`)
- 設計判断の変更(指摘があればユーザーへ)
- スコープ外の"ついで修正"(メモとして残すだけ)

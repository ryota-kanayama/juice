# orchestrate — 実装を子セッションへ出し、判断とレビューを手元に残す

**司令(このセッション)は設計判断とレビューを持ち、実装は子セッションへ出す。** 司令はプロダクトコードを書かない。書いた瞬間にレビューの独立性が消えるため。

言語・ビルドツールには依存しない。プロジェクト固有のコマンド(テスト・整形・静的解析)は Step 0 で確定し、子への指示に**そのまま埋めて渡す**。

## この分担の理由

1. **レビューの独立性** — 実装した頭がレビューすると、自分の前提を検査できない。書き手と検査役を別セッションに置くのが最も確実な分離。
2. **文脈の分離** — 実装の試行錯誤で司令の文脈を埋めない。司令は設計判断に必要なものだけを持ち続ける。
3. **並行** — 1作業ツリー1ブランチを守れば、独立した作業を同時に進められる。

**レビューは常に司令が持つ。** 子セッションのモデルや権限設定は司令と同じとは限らず、敵対的レビューの委譲(`sonnet` 指定のサブエージェント)が意図どおり効く保証がない。分離が要るならサブエージェントではなくセッションを分ける。

**この規則はスキルの規則とレビューで守る。** 機械のガードは持たない。司令が自分で直したくなったら、子へ差し戻すか、ユーザーに確認する。

## 役割

| | 司令 | 子 |
| --- | --- | --- |
| 担当 | 設計判断・要件の確定・Red失敗理由の確認・Refactor判断・レビュー・PR | 下表の作業 |
| サブエージェント | 用途に応じて明示指定して使う | 使わない(必要になったら司令へ相談) |

**子に出す作業**——判断ではなく作業であり、サブエージェント委譲が要らないものすべて。

| 作業 | 司令が先に固めるもの | 司令が後で受け取るもの |
| --- | --- | --- |
| テスト実装(Red) | テストリスト(**期待値は書かない**) | 失敗理由の妥当性判断 |
| プロダクトコード実装(Green) | 失敗しているテスト | Refactor判断・レビュー |
| 文書の下書き(CLAUDE.md・README・CHANGELOG) | 根拠となる決定(確定済み) | `doc-review` での品質ゲート |
| 調査・実測・検証スクリプト | 何を測るか | 数値の解釈と結論 |

**子に出してはいけないもの**: レビュー(impl-review / doc-review)、設計判断(方針や要件の決定)、PR作成。

## 1サイクルの回し方(TDDの場合)

**1サイクル = 1 worktree = 1ブランチ = 1 PR。**

実装以外の作業(文書執筆・調査)も骨格は同じ——司令が前提を固める → 子へ投入 → 司令が結果を判断する。違うのは4〜6の中身だけで、**レビューは常に司令が持つ**。

### 0. 司令: プロジェクトの前提を確定する

テストコマンド・整形/静的解析コマンド・テストの配置規約を、`CLAUDE.md` / `AGENTS.md` / ビルド設定(`package.json` / `Cargo.toml` / `pyproject.toml` / `go.mod` 等)から確定する。不明なままなら子に推測させず、ユーザーに確認する。以降の指示にはこの**具体的なコマンド文字列**を書く。

### 1. 司令: テストリストを作る

Issue・要件・受け入れ条件から「何を検証するか」を列挙する。**期待値は書かない**——入力と期待する結果の**種類**までにとどめ、具体値の算出は Red 子にさせる(期待値を渡すとテストが実装の写経になる)。

### 2. 子を立てる

作業ツリーを分ける(既存の作業ツリーを子と共有しない)。`worktree` スキルがあればその手順で切る。無ければ次で足りる。

```text
git fetch origin && git worktree add .claude/worktrees/<branch> -b <branch> origin/<既定ブランチ>
```

その作業ツリーで新しいセッションを起動する。セッション多重化ツール(`herdr` 等)があればそれで、無ければ端末を分けて手動で起動する。

**子は常に `--model sonnet` で起動する。** 例外は置かない。指定しないと子はセッションの既定モデルを継承し、手を動かすだけの子に判断用の上位モデルを使うことになる。判断とレビューは司令が持つので、子に上位モデルは要らない。`herdr` なら次の形になる。

```text
herdr agent start <名前> --kind claude --pane <pane-id> -- --permission-mode auto --model sonnet
```

**タスクを投入する前に、必ず子の入力モードを確認する。** 承認待ちで止まっているセッションへ長いプロンプトを投げると、宙に浮いたまま気づけない。自動実行に切り替える必要があるなら、**司令が代わりに承認を押さず、ユーザーに切り替えを依頼する**(ユーザーの許可判断を迂回することになる)。

#### 子を直接起動できないとき: 指示書で渡す

**司令が子を起動できないときは、指示書(ハンドオフ)をファイルに書き、貼り付け用の短い文面をユーザーに渡す。** ユーザーは新しいセッションを開き、文面を貼って子を立てる。長い指示を貼らせずファイルを読ませるのは、貼り付けの取りこぼしを防ぐため。

1. 指示書を主作業ツリーの `.claude/handoff/<番号>-<slug>.md` に書く(git 管理外)。番号は Issue 番号、無ければ `MMDD`。Red と Green は別の指示書にする(末尾に `-red` / `-green`)
2. 指示書には、Step 3・5 で子へ渡す内容をすべて書く。冒頭には作業ツリーの絶対パスと「そこへ移動して作業すること」を置く
3. 次の形の文面を、コードブロックでユーザーに渡す(コピーできるようにするため)。あわせて「Sonnet で起動したセッションに貼る」ことを伝える。司令のセッション名は `ListAgents` の先頭行で分かる

```text
🚩 ハンドオフ: <タイトル>

<タイトル>
<指示書の絶対パス> を最初に読み、その指示に従って着手してください。
司令のセッション名は <セッション名> です。
```

子の画面は司令から読めない。完了は子の報告(`SendMessage`、またはユーザーの中継)で知り、Step 3 の `git` コマンドで実物を確かめる。

### 3. Red子へ投入する

指示の冒頭に必ず入れるもの: **`.claude/skills/orchestrate/CHILD.md` を最初に読んで従うこと**、司令のセッション名(復路の宛先)。加えてテストリスト・対象の要件(Issue・設計メモ)の所在・テストコマンド・「プロダクトコードは変更しない」。

**非同期実行の戻り値を信用しない。** 待機付きの投入APIは、こちら側のタイムアウトで戻ることも、承認待ちを取りこぼして「完了」を返すこともある。戻ってきたら**必ず実物を確認する**。

```text
git -C <worktree> log --oneline -1     # コミットされたか
git -C <worktree> status --short       # 中途半端な変更が残っていないか
```

加えて子の画面を読み、最終状態(承認待ちで止まっていないか)を目視する。

### 4. 司令: Redの失敗理由を確認する

テストが**正しい理由で**落ちているかを見る。コンパイル/importエラーで落ちているのはRedではない。ここを飛ばすと、実装が無いのではなく書き間違いで落ちているテストを緑にしてしまう。

### 5. Green子へ交代する

Red子を終了させ、**同じ作業ツリーで**Green子を立てる。Red子とGreen子を同時に走らせない(1作業ツリー = 1ブランチのため)。

指示: 「テストを変更せず緑にする」「最小実装にとどめる」。CHILD.md の参照は同じ。

### 6. 司令: Refactorとレビュー

- テスト・整形・静的解析(Step 0 で確定したコマンド)を**司令が自分で**実行して確認する
- Refactorは司令が判断し、必要なら子へ差し戻す
- `impl-review` を司令が回す。レビュー済み台帳(`.claude/state/impl-reviewed-commits`)への追記は**作業対象の作業ツリー側**で行う(`.claude/state/` は作業ツリーごとに独立するため、別の作業ツリーへ書いても効かない)
- レビュアーには**変異解析**(実装をわざと壊してテストが落ちるか見る)を促す。削除・置換だけでなく「**意味論の深さを変える / 条件を広げる**」型を含めるよう指示する——後者だけが検出できる穴がある(`test-writing` スキルの変異解析節)
- レビュアーが報告した**数値は自分で実測してから**文書に書く(転記は誤りを増幅する)
- md変更があれば `doc-review`

### 7. PR

プロジェクトのマージ可能ルール(`CLAUDE.md` 等)に従い、司令がPRを作る。ユーザー向けの変更なら `CHANGELOG.md` の `[Unreleased]` 節への追記を忘れない(`CLAUDE.md` の規則)。マージは `--squash` 必須(フックが強制する)。

マージまで進めたら、司令が主作業ツリーから作業ツリーとブランチを片付ける。子セッションを先に終了させる(作業ツリーの中にいるプロセスがあると消せない)。手順は `worktree` スキル。無ければ、PR がマージ済みで、ブランチに PR 外のコミットが無く、作業ツリーに未コミットの変更が無いことを確かめてから、`git worktree remove`(`--force` なし)とローカル・リモートのブランチ削除を行う。そのサイクルの指示書(`.claude/handoff/`)があれば、あわせて消す。

## 連絡

- **往路**: 司令から子へ直接投入する(セッション多重化ツールの投入コマンド、または端末での貼り付け)。直接投入できなければ指示書で渡す(Step 2)
- **復路**: 子から `SendMessage`。宛先は `ListAgents` が表示する形式(名前だけでは拒否されることがある)
- **受信の前提**: `crossSessionInbound: "accept"` が要る。**ユーザー設定(`~/.claude/settings.json`)か `/config` で設定する**——プロジェクト設定は「既定より厳しいときだけ」適用されるため、`accept` を書いても効かない。起動時に読まれるので、設定より前に始めたセッションでは有効にならない
- **疎通しないとき**: 子の画面を直接読む。片方向でも進行は止まらない

## やらないこと

- 司令がプロダクトコードを書く(テストリストの作成までにとどめる)
- 子にレビュー(impl-review / doc-review)をさせる
- 子にサブエージェントを使わせる(分離が要るならセッションを分ける)
- Red子とGreen子を同時に走らせる
- 子が権限で拒否された操作を司令が代行する(権限の迂回になる。ユーザーへ返す)

## 粒度の違い

Red/Greenの分離は**サブエージェント**でも作れる(`tdd`)。このスキルは同じ分離を**別セッション+別作業ツリー**で作る。目的(テストが実装に引きずられるのを防ぐ)は同じで、粒度と隔離の強さが違う。実装を外へ出さないなら前者で足りる。

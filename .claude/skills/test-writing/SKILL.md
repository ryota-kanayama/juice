# test-writing — テストの書き方規約

役割分担: **tddスキル**=プロセス(Red→Green→Refactor)、**このスキル**=具体的な書き方。
プロジェクトにテスト戦略文書があればそれが層構成の正で、このスキルは1本1本の書き方を定める。

言語・フレームワークには依存しない。例はRustで書いてあるが、規約自体はどの言語にも当てはまる。juice 固有の事情は末尾の「プロジェクト固有の追記」にある。

## Step 0: プロジェクトの前提を確定する(毎回)

次を確認してから書き始める。不明なまま推測で走らない。

| 確認するもの | 探す場所 |
| --- | --- |
| テストコマンド(全体・単体) | `CLAUDE.md` / `AGENTS.md` → `package.json` scripts / `Cargo.toml` / `pyproject.toml` / `Makefile` / `go.mod` |
| 整形・静的解析コマンド | 同上(Greenの成功条件に**必ず含める**) |
| テストの配置と命名 | 既存テスト(規約はコードに倣う。新しい流儀を持ち込まない) |
| テストフレームワークの流儀 | 既存テスト(アサーション関数・セットアップの作法) |

確定したコマンドは、サブエージェントや子セッションへの指示に**文字列としてそのまま埋める**。「プロジェクトのテストを実行」では環境差で外す。

## 配置と命名

- 既存テストと同じ場所・同じ流儀に置く。新規に階層を作るのはユーザーの承認を得てから。
- テスト名は「入力→期待」を表す(例: `empty_source_produces_no_tokens` / `expired_token_is_rejected`)。言語の命名規約(snake_case / camelCase)は既存に倣う。**テスト名の説明文がプロジェクトの作業言語で書かれることもある**(文字列リテラルとして渡すフレームワークでは識別子の制約を受けない)。
- テスト名(`it('…')`)が、失敗時に「何が壊れたか」を読ませる。名前だけでは入力の意図が伝わらないときだけ、**1文のコメント**で補う(例: 「09:00〜12:00 休憩0 → 実労働180分」)。

## 1テスト=1検証項目

- **assertは原則1つ。** 複数入力を検証したいときは関数を分ける。前提確認(「Okであること」の取り出し等)はassert数に数えない。
- パラメータ化テストの機構は原則使わない——関数分割なら「テスト名=仕様文」の価値が保てる。
- 同一検証項目の複数入力は代表1入力に統合してよい。ただし**統合前に、元の各入力が検証していた境界が代表入力にも残るか確認する**。
  - 教訓: `_tmp` と `_1` を `_tmp1` に統合したら「`_` 直後が数字」の並びが消えた。これは別検証項目であり統合できない。
- **AAAパターン(空行区切り)**: テスト本体を Arrange(準備)/ Act(実行)/ Assert(検証)の3ブロックに分け、**空行で区切る**。juice のテストは `// Arrange` などのマーカーコメントを付けない流儀なので、既存に倣って付けない。Arrangeが入力1行でも省略しない。入力は変数に束縛してActで使う。スナップショットテストは対象外。

## 期待値の書き方

- **丸ごと明示する。** `assert_eq!(tokens, vec![Token { kind: TokenKind::Int, text: "42".to_string() }])` のように、期待する値そのものを書く。`is_ok()` / `toBeTruthy()` / `assertIsNotNone` 等の曖昧検証は不可。
- 失敗メッセージは「〜であること」の形で書く(失敗時にそのまま仕様文として読める)。
- **例外(巨大入力)**: 期待値の丸ごと明示が非現実的な生成入力(64段ネスト等)に限り、形状検証(件数等)まで緩めてよい。理由をコメントに明記する。境界の検知力は**対になる負例**(65段=エラー)が担保する。
- **例外(負例の語彙表ループ)**: 最初のエラーで停止する処理では、多数の語を1入力に併合できない。この場合に限り配列+ループで全語を検証してよい。**失敗メッセージに必ず語名を含める**(どれで落ちたか分からないループは検知力を失う)。正例の語彙表は1入力に並べて検証する——ループにしない。

## 負例テスト(エラーになるべき入力)

- 期待値は**エラーを丸ごと明示**する(種類+原因箇所。エラー型にコード・位置があればそれも)。`is_err()` や種類だけの検証は不可——原因箇所の劣化を検知できない。
- **原因箇所は違反した入力をピンポイント**で指す。「入力全体」を指す実装は、利用者に直し方を示す精度が出ないため不可。
- テスト名に何が不正かを含める(例: `不正な時刻形式は保存せずエラーにする`)。
- エラー種別は**文字列でなく列挙型/定数**で表す(タイポで存在しない種別を作れない)。
- 同一規則の負例なら、境界の異なる複数ケースを同じ関数に入れてよい。

## 要件との対応

- 守るべき要件・不変条件(`CLAUDE.md` の「時刻の不変条件」など)は、**境界を1つずつ別のテスト**にする(下限ちょうど・端数の丸め・不正な形式)。
- 要件の負例のうち**未実装機能に依存するケースは先取りしない**。コメントに「〜のサイクルで追加」と送り先を明記し、実装サイクル側で拾う。

## TDDサイクル中の分担

- **Redのスタブ規則**: テストのコンパイル/import に必要な定義のみ追加してよい(型・シグネチャ。中身は `todo!()` 相当)。ロジックは1行も書かない。「コンパイル/importエラーで落ちる」はRedではない——assertionまたは意図的なpanicで落ちること。
- **Greenの最小主義**: テストに無い挙動を先取りしない。例: 未対応入力は最小のエラーを返す(黙って読み飛ばすのは暗黙の仕様決定になるので不可)、分岐は1件のif比較で足りる(表への一般化はテストが増えてから)。
- **Refactorはメイン**: 2回出たパターンは部品化する。リファクタ後に全テスト+整形+静的解析を再実行。

## スナップショット/ゴールデンテストの併用

- **TDDサイクルの検証には使わない**(期待値明示のassertで回す)。サイクル群の完了後に**回帰の網**として追加する。
- 初回生成したスナップショットは**必ず目視レビュー**してからコミットする(生成物を無検査で正としない)。
- 差分が出たら「実装のバグ」か「仕様の意図的変更」かを判断し、後者のみ更新する。

## 変異解析(ミューテーションテスト)でテストの網を検査する

**テストが全部緑でも、網が粗いことはある。** 実例: 142本すべて緑の状態から実装をわざと壊すと次々と素通りし、穴は7つ見つかった。テストを159本に増やして初めて全変異が落ちるようになった。

変異解析とは、実装をわざと壊してテストが落ちるかを見る手法。注入した壊し方を「変異」、変異に対してテストが落ちないことを「生存」と呼ぶ。生存は「その変異を検知するテストが無い」ことの証拠で、テストの**数**ではなく**検知力**を測れる。

### 変異の3類型

変異の型によって見つかる穴が違う。3類型すべてを回すこと。

| 型 | 変え方 | 例 |
| --- | --- | --- |
| 削除・置換 | 条件を消す・一覧の項目を足し引きする・写像を取り違える(1箇所の機械的な変更) | `stack.pop()` を `clear()` に替える / 判定表に1項目足す / 2種類の記号を同一視する |
| 意味論の深さ | 参照の仕組み自体を替える | 「スタックの先頭だけ見る」を「末尾から探して同種が見つかればそこまで戻す」に替える(回復処理でよくある別実装) |
| 条件を広げる | ガードから限定条件を外す | 先読みのガードから種別条件を外す(結果: 想定外の並びまで同じ扱いになる) |

- 削除・置換型は1ラウンド目で見つかる。後者2型は見落としやすく、テストを増やしてもなお生存しがち。
- 後者2型の正体は「実装を弱くする」変化ではなく「**もっともらしい別実装**」への差し替え。実装者もレビュアーも書きそうなコードだから、将来の退行として現実に起きる。

### なぜ後者2型を忘れがちか

境界値のテストが「深さ1」に偏ると、正しい実装と別実装の区別がつかなくなる。

- 深さ1(スタックに要素が1個)では、「先頭だけ見る」と「末尾から探す」は同じ結果を返す。区別には**深さ2+種類の違う対象**が要る。
- ガードも同じ理屈。ガード内の条件に当たる入力だけを試すテストは、ガードの有無を区別できない。**ガード条件から外れる入力**が要る。
- 教訓: 「境界の入力を1組」だけでは足りない。深さを変え・種類を変えて、同じ規則の別の面を突く入力を揃える。

### 手順と安全規則

1変異ずつ「注入→実行→復元」で回す。

1. `git status` がクリーンであることを確認する。
2. 変異を1つ注入する。
3. テストを実行し、落ちたか生存したかを記録する。
4. **必ず元に戻す。** `git checkout -- <対象ファイル>` で復元し、`git status` と `git diff` で汚れが残っていないことを確認してから次の変異へ進む。

- 復元忘れは壊れた実装をそのままコミットする事故になる。毎回 `diff` でバイト一致まで確認する。
- 生存した変異には、殺すテストとの対応を記録する(どの変異がどのテストで落ちるか)。テスト統合の判断材料になる。
- 生存を塞ぐテストは**要件から期待値を導いて**書く。変異後の実装に合わせて書くと、変異が基準にすり替わる。

### いつ回すか

- **コードレビューで「仕様適合とテストの穴」を見る役への指示に含める**(`impl-review` の観点A)。レビュアーは対象が守るべき要件・不変条件ごとに変異を注入して検査する。
- 全テスト緑でも変異が1つでも生存したら「テストの穴」として指摘する。深刻度は**重大 / 改善 / メモ**に分類する——重大は再現テストを書いて直す、改善はその場で直す、メモは残すだけ。
- 毎サイクル回す必要はない。再レビューやフェーズ完了のように、テストの網に確信が欲しい節目で回す。

## プロジェクト固有の追記

このスキルは言語非依存の規約を中心に持つ。プロジェクト固有の事情(実行コマンドの癖・固有のテスト層)は、**プロジェクトの `CLAUDE.md` かこのファイルの末尾に追記**して育てる。確立していない領域は「未確立」と書き、確立したら追記して消す。

### juice の事情

- **コマンド**(正は `CLAUDE.md`):
  - フロント・共有・lambda: `npm test`(単体は `npx vitest run <ファイル>`)
  - 型・静的解析: `npm run typecheck` / `npm run lint`
  - Rust バックエンド: `cd src-tauri && cargo test --lib`
- **配置**: フロントのテストは対象と同じ場所の `*.test.ts(x)`。共通のテストデータは `frontend/renderer/src/test/factories.ts`(`makeSession` など)を使い、テストごとの重要な値だけ上書きする。`window.bridge` は各テストで `vi.stubGlobal` する。
- **決定的にする**: 乱数・現在時刻・タイマーに依存させない(`Math.random` のスタブ、固定の日付、`vi.useFakeTimers`)。
- **データ**: テストは実ファイルの `Juice/`(本番データ)にも `juice-dev/` にも触れない。ストアは一時ディレクトリで検証する。
- **変異解析**: Stryker(設定は `stryker.conf.json`、`npx stryker run`)。対象は `domain`・`hooks`・`daily`・`shared`・`lambda`。Rust 側は未確立で、上の手動手順で回す。

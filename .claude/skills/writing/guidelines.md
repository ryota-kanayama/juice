# 読みやすい日本語文書の指標と根拠(出典集)

SKILL.md のルールの根拠となる調査結果(2026年8月調査)。ルールの背景を確認したいとき、
判断に迷う表記が出たときに参照する。§6 は正本型文書(設計書・仕様書)向けの構成原則で、
このリポジトリの SKILL.md §1 はそれに基づく。

## 2. 定量指標の根拠

| 指標 | 数値 | 根拠 |
| --- | --- | --- |
| 一文の長さ(警戒ライン) | 50〜60字 | 公用文作成の考え方・解説「50〜60字ほどになってきたら読みにくくなっていないか意識するとよい」(一次確認済み) |
| 一文の長さ(通説) | 40〜60字 | 心理学者・波多野完治が米国の文章心理学を日本語に応用した数字とされる |
| 一文の上限(機械チェック) | 100字(厳格運用は90字) | [textlint-rule-preset-ja-technical-writing](https://github.com/textlint-ja/textlint-rule-preset-ja-technical-writing) デフォルト |
| 読点の数 | 1文に3つまで | 同上(textlintデフォルト) |
| 漢字の連続 | 最大6文字 | 同上 |
| 漢字含有率 | 20〜30%(30%超で硬く、40%で読みにくい) | 「漢字3割」通説。筑波大の研究が引用されるが論文原典は出典未確認 |
| 段落の長さ | 3〜5文、150〜300字 | 実務通説(Webでは2〜3文も一般的) |

**リーダビリティ研究の裏付け**: jReadability(李在鎬・早稲田大)の回帰式では、
**平均文長と漢語率が文章難易度を上げる二大要因**(R²=0.896)。
「文を短く」「漢語を減らして和語に」という定性ルールに定量的裏付けがある。
出典: [jReadability](https://jreadability.net/)、[李論文PDF](https://researchmap.jp/jhlee/published_papers/1284306/attachment_file.pdf)

## 3. 公用文「文の書き方」原則(建議Ⅲ-3、一次確認済み)

- ア. 一文を短くする
- イ. 一文の論点は一つにする
- ウ. 三つ以上の情報を並べるときは箇条書を利用する
- エ. 基本的な語順(いつ・どこで・誰が・何を・どうした)を踏まえて書く
- オ. 主語と述語の関係が分かるようにする
- カ. 接続助詞や中止法を多用しない
- キ. 同じ助詞を連続して使わない
- ク. 複数の修飾節が述部に掛かるときは、長いものから示すか、文を分ける
- ケ. 受身形をむやみに使わない
- コ. 二重否定はどうしても必要なとき以外は使わない
- サ. 係る語と受ける語、指示語と指示される語は近くに置く
- シ・ス. 係り方・読点の位置による多義性に注意する

構成については建議Ⅲ-4:「結論は早めに示し、続けて理由や詳細を説明する」
「文書の結論は、できれば最初の段落で示しておく」「見出しを追えば全体の内容がつかめるようにする」。

## 4. 修飾語と読点の原則(本多勝一『日本語の作文技術』)

- 語順4原則: (1)節を先に、句を後に (2)長い修飾語ほど先に (3)大状況から小状況へ (4)親和度の低い語順に
- 読点2原則: (1)長い修飾語が2つ以上あるときの境界に打つ (2)語順が原則の逆になったときに打つ
- 参考: [要約(名古屋大)](https://www.math.nagoya-u.ac.jp/~shinichiroh/2018/02/13/japanese-punctuation.html)

## 5. カタカナ語の4分類(公用文)

1. **定着した語はそのまま**: ストレス、ボランティア、リサイクル、リスク、コスト
2. **言い換える**: アジェンダ→議題、インタラクティブ→双方向的、サプライヤー→仕入先
3. **言い換え困難なら説明を付ける**: インクルージョン(多様性を受容し互いに作用し合う共生社会を目指す考え)
4. **定着途上の語は使い方を工夫**: 「リスクを取る」→「覚悟を決めて進む」

言い換えの標準リソース: [国立国語研究所「外来語」言い換え提案](https://www2.ninjal.ac.jp/gairaigo/)

## 6. 正本型文書(設計書・仕様書)の構成原則(2026年8月調査)

調査レポート・企画書向けの「文書冒頭の TL;DR・PREP」は、節構造で参照される設計書・仕様書には
合わない。reference 型の文書には次の原則を適用する(SKILL.md §1 の根拠)。

| 原則 | 内容 | 出典 |
| --- | --- | --- |
| reference は事実を淡々と | 参照資料には事実(規範)だけを書き、意見・推測・解釈・手順の指導を混ぜない。理由や背景は explanation(このリポジトリでは設計方針)へ分離する | [Diátaxis: Reference](https://diataxis.fr/reference/) |
| 一貫した構造(標準パターン) | 同種のページ・節は同じ構成・同じ順序で書く。一貫性があって初めて参照資料は「引ける」。構造は対象(プロダクト)の構造を写す | 同上・[Diátaxis](https://diataxis.fr/) |
| 例は教えずに示す | 例はコピーして使える短いものにする。チュートリアルにしない(仕様の正例・負例はこの形) | [Diátaxis: Reference](https://diataxis.fr/reference/) |
| 結論先行は「節単位」で適用 | 公用文建議Ⅲ-4「結論は早めに示し、続けて理由や詳細を説明する」は、参照型文書では文書全体ではなく各節に適用する(節冒頭で決定・規範を言い切る)。文書全体の要旨は冒頭の正本宣言が兼ねる | 建議Ⅲ-4(§3参照)+ [Google developer style guide](https://developers.google.com/style/highlights)(最重要情報を先頭に) |
| 図表は理解の近道に限る | 状態遷移・フロー・比較など、散文より速く伝わるものだけ図表にする | [Qiita Team: 技術仕様書を読みやすくするテクニック](https://teams.qiita.com/tech-specifications-writing-tips/) ほか実務記事 |

## 7. 機械チェックの導入(将来の選択肢)

Markdown資料のCI的な自動検査には
[textlint-rule-preset-ja-technical-writing](https://github.com/textlint-ja/textlint-rule-preset-ja-technical-writing)
が本ガイドの基準をほぼ実装している(一文100字以内 / 読点3つまで / 漢字連続6字まで /
二重否定禁止 / 冗長表現検出 / 文体統一)。導入する場合は Node.js + textlint をセットアップし、
Hooks(PostToolUse で Write/Edit 後に実行)と組み合わせると保存時の自動検査ができる。

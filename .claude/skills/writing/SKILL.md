# writing — 読みやすい日本語文書の執筆ルール

このリポジトリの文書は2種類ある。

- **参照される正本**: `CLAUDE.md`・スキル・設計メモ。通読される読み物ではなく、「探している事実へ最短で辿り着ける」ことを優先する。§1〜§4 をすべて適用する
- **利用者に読まれる文書**: `README.md`・`CHANGELOG.md`。専門知識のない利用者が読む。§2〜§4 を適用し、§1 の構成ルールは節の型を揃える範囲にとどめる

一度で理解できる文章だけを書く。根拠と出典は同ディレクトリの [guidelines.md](guidelines.md) を参照。

このスキルは**どう書くか**だけを扱う。何を書くか(`CHANGELOG.md` に載せる変更の範囲など)は `CLAUDE.md` が正。

## 使い方(2つのモード)

1. **執筆モード(自動)**: このリポジトリで文書を書く・編集するときは、以下のルールを(文書の種類に応じて)適用する。
2. **診断モード(手動)**: `/writing <ファイルパス>` と呼ばれたら、`$ARGUMENTS` のファイルを読み、下記チェックリストに照らして問題箇所を「該当箇所の引用 → 問題点 → 修正案」の形式で列挙する。ユーザーが修正を求めたら書き直す。引数なしで呼ばれたら、直近に編集した文書を対象にする。

## 1. 構成のルール(文書レベル——正本型文書向け。`CLAUDE.md`・スキル・設計メモ)

- **節の冒頭で決定・規範を言い切る**(節単位の結論先行): 各節は「決定・規範(太字)→ 理由 → 詳細・例外」の順。通読向けの TL;DR・要約は**書かない**——文書の冒頭は目的と参照先だけに留め、以降は各節が独立して読める reference 構造にする。
- **同種の節は同じ型で書く**: 構成・順序を揃える(`CLAUDE.md` の各節、スキルの「手順」「やらないこと」など)。型が揃っていると、拾い読みが効き、欠けている情報にも気づける。
- **事実と意見を混ぜない**: 規範や現状(事実)の節に、解釈や推測を挟まない。理由・トレードオフ・経緯は別の節に分ける。
- **見出しだけで全体がつかめるようにする**: 見出しは論点を端的に示す(「検討」ではなく「totalTime は区間の合計から導出」)。
- **3つ以上並べるなら箇条書き**: 文中に3つ以上の項目を並べない。列挙は箇条書き、属性の比較は表を使う。表には必ずタイトルか導入文を付ける。
- **1段落1トピック**: 段落は3〜5文(150〜300字)を目安に。テーマが変わったら段落を分ける。
- **図は構造・流れに限って使う**: 状態遷移・依存の向き・データの流れなど、散文より図が速いものだけ。飾りの図は作らない。

## 2. 文のルール(センテンスレベル)

- **一文は60字以内を目安、100字を上限とする**。長くなったら文を分ける。**例外**: 手順やコマンドを並べた箇条書きの1項目は、コード片を含めて100字を超えてよい。ただし論点は1つに保つ。
- **一文の論点は1つ**。「〜が、〜ので、〜であり、」と接続助詞でつなげ続けない。
- **読点は1文に3つまで**。読点は係り受けを明確にする位置に打つ。
- **主語と述語を近づける**。係る語と受ける語、指示語と指される語も近くに置く。
- **修飾語は長いものから先に**置く。複数の修飾節が1つの述語に掛かるなら文を分ける。
- **受動態をむやみに使わない**。動作の主体を主語にして能動態で書く。
- **二重否定は禁止**。「〜しないわけではない」→「〜することもある」。
- **同じ助詞を連続させない**。特に「の」の3連続は書き直す(「本年の当課の取組の中心」→「本年、当課が中心的に取り組むのは」)。
- **冗長表現を削る**:

  | 冗長 | 簡潔 |
  | --- | --- |
  | 〜することができる | 〜できる |
  | 調査を実施した | 調査した |
  | 〜ということになる | 〜である |
  | 〜という形になっている | 〜している |
  | 約20名くらい | 約20名 |
  | まず最初に | まず |

- **曖昧語を期日・条件に置き換える**: 「早めに」→「1週間以内に」、「適切に」→ 具体的な判定条件。ただし**列挙の件数は文中に書かない**(「次の3つ」は項目の増減で古びる)。

## 3. 語彙のルール(単語レベル)

- **漢字率は2〜3割を目安にする**(漢字が4割を超えると読みにくい)。漢字を6文字以上連続させない。
- **形式名詞・補助動詞はひらく**(ひらがなで書く):

  | とじる(×) | ひらく(○) | とじる(×) | ひらく(○) |
  | --- | --- | --- | --- |
  | 事 | こと | 出来る | できる |
  | 時 | とき | 更に | さらに |
  | 所 | ところ | 但し | ただし |
  | 物・者 | もの | 及び/又は | および/または |
  | 為 | ため | 尚 | なお |
  | 様々 | さまざま | 即ち | すなわち |
  | 〜て下さい | 〜てください | 予め | あらかじめ |
  | 〜て頂く | 〜ていただく | 且つ | かつ |

  ただし実質的な意味を持つ場合は漢字のまま(「賞状を頂く」「家を建てる所」)。
- **カタカナ語は4分類で扱う**: (1)定着語はそのまま(リスク、コスト) (2)言い換え可能なら日本語に(アジェンダ→議題) (3)言い換え困難なら初出で括弧説明を付ける (4)判断に迷う語は使わない。技術用語(スキーマ、トリガ等)は (1) 扱いでよいが、文書内で表記を統一する。
- **専門用語は初出で説明する**。言い換えられるなら平易な語に。
- **「等」「など」は代表例を2つ以上挙げてから使う**。単独の「等」でごまかさない。
- **「的」「化」を1文に2回以上使わない**。
- **根拠のない断定を書かない**: 理由・数値には根拠を付ける。このリポジトリではコード・`CLAUDE.md`・外部の一次資料へのリンクが出典に相当する(値は転記せずリンクする)。

## 4. 表記統一のルール

- 文体は1文書内で統一する。正本型文書は「である調」(箇条書き・表内は体言止め可)、利用者向けの `README.md`・`CHANGELOG.md` は「です・ます調」。
- 句読点は全角の「、」「。」。半角カンマ・ピリオドは使わない。
- 括弧・記号は**文書内の主たる表記に合わせる**。混在している文書では全面置換をせず、触れた箇所だけ多数派に揃える。新規文書は半角 `()` を使う。固有名詞は原表記のまま引用する。
- 表記ゆれを作らない。同じ概念には同じ語を使う(サーバ/サーバー、ユーザ/ユーザー等は文書内で統一)。用語は `CLAUDE.md` やアプリ画面上の表記に揃える。

## 診断モードのチェックリスト

`/writing <ファイル>` で呼ばれたら、次の順に検査して報告する。

1. **構成**: 節の冒頭に決定・規範があるか / 同種の節の型が揃っているか / 事実と意見が混ざっていないか / 見出しだけで内容がつかめるか / 長い列挙が文中に埋まっていないか
2. **文**: 100字超の文 / 読点4つ以上の文 / 二重否定 / 受動態の乱用 / 「の」の3連続
3. **語彙**: とじるべき漢字(上の表) / 説明なしの専門用語・カタカナ語 / 冗長表現 / 単独の「等」/ 根拠のない断定
4. **表記**: 文体の混在 / 表記ゆれ / 括弧・記号の不統一

報告形式:

```text
## 診断結果: <ファイル名>
- 重要度高(意味が取りにくい箇所): N件
- 重要度中(冗長・ルール違反): N件
- 表記ゆれ・軽微: N件

### 重要度高
1. L42「<原文引用>」
   問題: 一文118字・論点が2つ
   修正案: 「<修正文>」
...
```

指摘は多くても15件までに絞り、影響の大きい順に並べる。機械的な全列挙はしない。

## 他スキルとの関係

- 文体ガイドを求める検査(`doc-review` の文言品質など)の参照先になる(参照する側はこのスキルの存在を前提にしない)。
- 文書を書き終えたら markdownlint を実行する(プロジェクトの規則)。
